# Theophysics Claims Layer — Protocol Specification
## Version 1.0 | POF 2828 | faiththruphysics.com

---

## PURPOSE

This document defines the claims injection protocol for the Theophysics web series.

Any AI, any tool, any human following this spec produces output that:
1. Renders correctly on every series page
2. Is human-reviewable before going live
3. Coordinates across the full series
4. Survives upgrades to the underlying site

Read this document before generating, reviewing, or rendering claims.

---

## THE CONTRACT IN ONE PARAGRAPH

Each HTML series page has a sidecar claims file — a plain JSON file in the same directory.
The claims file contains formal claims extracted from that page, each with a classification,
a status, and a location (which section it appears after). The page renderer reads the sidecar
on load and injects approved claims into the DOM. Nothing in the HTML itself changes.
Humans review the JSON. AIs generate and revise the JSON. The HTML stays clean.

---

## FILE NAMING CONVENTION

For page: `MDA-003-measuring-moral-health.html`
Sidecar:  `MDA-003-claims.json`

Rule: take the series prefix and number (first two hyphen-separated segments), append `-claims.json`.

Examples:
  MDA-003-measuring-moral-health.html → MDA-003-claims.json
  GTQ-001-genesis-to-quantum.html     → GTQ-001-claims.json
  ONE-005-the-hinge.html              → ONE-005-claims.json

---

## CLAIM OBJECT SCHEMA

```json
{
  "claim_id":       "string — unique within series, e.g. MDA-003-C1",
  "after":          "string — data-name value of the section this claim follows",
  "classification": "load-bearing | suggestive | overreached",
  "status":         "pending | approved | rejected | flagged",
  "text":           "string — the claim in plain English, 1-3 sentences",
  "series_role":    "introduced | evidenced | verified | challenged",
  "evidenced_in":   ["array of page IDs where this claim is supported, e.g. MDA-007"],
  "reviewer_notes": "string — human or AI notes on this claim",
  "generated_by":   "string — model/tool that produced this claim",
  "generated_date": "string — ISO date"
}
```

---

## CLASSIFICATION DEFINITIONS

**load-bearing**
The argument collapses if this claim is false. The article's thesis depends on it.
Examples: "χ = 0.24 is below the critical threshold" / "The equation has three independent derivations"

**suggestive**
The claim is supported by evidence but does not alone carry the argument.
Examples: "Historical cases fit the decay model" / "The Amish data supports the restoration thesis"

**overreached**
The claim goes further than the evidence in this article supports.
Flag these. They are not necessarily wrong — they may be supported in other parts of the series.
Examples: "This proves God exists" / "Recovery is impossible without Christianity"

---

## STATUS DEFINITIONS

**pending**
Generated by AI, not yet reviewed by human. Does not render on the page.

**approved**
Human-reviewed and accepted. Renders on the page.

**rejected**
Human-reviewed and rejected. Stays in the JSON for audit trail but does not render.

**flagged**
Requires attention — may be correct but needs revision, citation, or demotion.
Does not render until promoted to approved.

---

## SERIES_ROLE DEFINITIONS

**introduced**
This is the first page in the series where this claim appears.

**evidenced**
This page provides supporting evidence for a claim introduced elsewhere.

**verified**
This page provides formal proof, data, or structural confirmation.

**challenged**
This page explicitly stress-tests or complicates a prior claim.

---

## THE AFTER FIELD

The `after` field must match the `data-name` attribute of an HTML section in the target page.

To find valid values, look for `data-component="section"` elements:
```html
<section data-component="section" data-name="section-trajectory"> ← use "section-trajectory"
```

If no matching section exists, use `"end"` to append after the last section.

Do NOT use CSS selectors, IDs, or class names. Use data-name only.

---

## WHAT AN AI MUST DO TO GENERATE CLAIMS

1. Read the target HTML page in full.
2. Identify every explicit or implicit claim — a statement that asserts something is true.
3. For each claim:
   a. Write it plainly in 1-3 sentences.
   b. Classify it: load-bearing / suggestive / overreached.
   c. Identify which section it follows (match to a data-name value).
   d. Assign series_role: where in the series arc does this claim sit?
   e. List which other pages evidenced_in (by ID) if you know them.
4. Set status to "pending" — never "approved". Only humans approve.
5. Set generated_by to your model name.
6. Output a valid JSON array following the schema above.
7. Do not invent claims. Do not paraphrase claims beyond what the page actually says.
8. Do not approve your own claims.

---

## WHAT A HUMAN REVIEWER MUST DO

1. Open the claims JSON file.
2. For each claim:
   a. Read it. Does it accurately represent what the page says?
   b. Is the classification correct?
   c. Is the series_role correct?
   d. Change status to: approved / rejected / flagged.
   e. Add reviewer_notes if needed.
3. Save the file.
4. Reload the page — approved claims render immediately.

---

## WHAT THE RENDERER DOES

The renderer (`mtl-claims.js`) automatically:
1. Derives the sidecar filename from the current page URL.
2. Fetches the JSON.
3. For each claim with status "approved":
   - Finds the element with matching data-name.
   - Inserts the claim block immediately after it.
   - Applies classification styling (load-bearing = amber / suggestive = gray / overreached = red).
4. Claims with status "pending", "rejected", or "flagged" do not render.
5. When "Claims" mode is active in the MTL reader bar, all approved claims are visible.
6. When "Claims" mode is inactive, claims are hidden by default.

---

## COORDINATION ACROSS THE SERIES

The `evidenced_in` field creates cross-series links.
A future series navigator will show: "This claim is introduced here and supported in Parts 3, 5, and 7."

For now: populate `evidenced_in` with known page IDs (e.g., ["MDA-007", "MDA-038"]).
Leave as empty array `[]` if unknown.

---

## VERSIONING AND DURABILITY

- This spec is versioned. The current version is 1.0.
- Each claims file should include a `"spec_version": "1.0"` field at the top level.
- When the spec changes, old files remain valid — the renderer is backwards-compatible.
- Do not invent new fields. If you need a field that doesn't exist, propose it as a spec revision.
